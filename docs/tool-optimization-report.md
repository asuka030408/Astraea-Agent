# Astraea Agent 工具调用优化报告

## 结论

本次实现了动态工具定义加载、原生工具并行、程序化只读计划、模型可见工具结果压缩、只读缓存、显式文件预取，以及工具定义压缩。完整工具结果和会话记录仍保存在本地。

**最终版本的真实模型配对测试**：7 类任务各重复 2 次，基线和优化版均为 **14/14 正确，正确率均 100%，提升 0 个百分点**。基线总耗时 20,647.5 ms，优化版 16,235.1 ms；平均每任务由 1,474.8 ms 降至 1,159.7 ms，**本样本快 21.37%**。模型可见工具调用数由 17 降至 14（减少 17.6%），但批处理内部仍执行对应的实际文件读取。样本较小、模型与网络耗时波动明显；调试阶段也曾出现耗时回退，因此这不是稳定提速的保证。

## 七项策略的实际改动

| 策略 | 实现与适用范围 | 正确性边界 |
| --- | --- | --- |
| 动态工具加载 | 每次模型请求从完整工具目录选择与当前问题相关的定义；`search_tools` 查目录，`load_tools` 在下一次模型调用中显式启用遗漏工具。实际执行节点仍注册全部工具。 | 规则式路由可能漏掉表达含糊的需求，发现工具作为补救入口。MCP 服务进程仍按原方式连接，动态的是**发送给模型的工具定义**。 |
| 工具并行调用 | LangGraph 可同时处理模型一次发出的独立调用；新增只读批处理最多 8 步、并发上限 4，结果保持输入顺序。 | 为避免共享 stdio 会话混用，请求同一 MCP 适配器的调用继续串行；写入、删除等不进入批处理。 |
| 程序化工具调用 | `run_readonly_plan` 一次执行 `read_file`、`read_file_lines`、`list_files`、`file_info`、`search_files` 等独立步骤，无需模型为每一步重新规划。 | 每步有有界预览与完整结果 ID；不支持任意代码、跨步骤依赖或修改型工具。 |
| 工具结果压缩 | 超过 2,500 字符的结果只在模型视图中压缩。结构化列表保留条目数、关键字段与外部 ID；普通文本保留首尾、相关行与外部 ID。 | 全文先写入会话专属外部记录；模型可用 `load_context` 读取。压缩片段可能遗漏细节，不能当作全文。 |
| 工具调用缓存 | 仅缓存 `read_file`、`read_file_lines`、`list_files`、`file_info`；键包括工具参数、工作区和目标的大小及时间戳，TTL 为 120 秒，最多 128 项。 | 文件变动会形成新键；错误不缓存。写入、删除、时间和 MCP 修改操作不缓存。缓存仅在当前进程的会话对象中有效。 |
| 工具调用预测 | 用户明确要求读取且写出工作区文件路径时，最多提前读取 2 个现有文件；读取与模型规划同时进行，若模型随后调用相同 `read_file`，直接复用结果。 | 只预测只读文件操作；不猜测写入或网络操作。预测未命中会造成额外一次读取。 |
| 工具定义压缩 | 将工具及参数描述缩短，移除不影响调用的标题和示例字段；保留工具名、参数类型与必填字段。 | 实际模型已验证本地工具调用；本地 MCP 定义完成转换与预算测量，复杂 MCP 调用仍需实测。描述过短可能影响工具选择。 |

实现主要在 `astraea/tool_runtime.py`。`astraea/agent.py` 绑定中间件；`astraea/context.py` 只压缩模型可见结果，完整工具消息仍进入会话历史；`astraea/mcp_tools.py` 在模型规划期间启动显式文件预取。

## Token 与速度量化

### 工具定义

在当前工作区启用的本地 MCP 目录下，共有 **55 个注册工具**（14 个内置、4 个会话上下文、3 个运行时、34 个 MCP）。按 `cl100k_base` 估算：

| 同一工具目录的请求形式 | 定义数 | 工具定义 tokens | 相对完整定义 |
| --- | ---: | ---: | ---: |
| 全部原始定义 | 55 | 7,330 | 基线 |
| 全部定义只压缩描述 | 55 | 6,371 | 减少 13.1% |
| “读取 note.txt”动态选择并压缩 | 3 | 238 | 减少 96.8% |

真实模型的 14 对本地文件任务中，基线每次模型请求的工具定义为 1,588 tokens；优化版平均为 346.9 tokens，**减少 78.2%**。这测量的是发送给模型的定义长度，不等于总账单或总体延迟节省。

### 受控微基准

`tests/benchmark_tool_optimization.py` 在相同结果上注入 30–50 ms 的可控 I/O 等待，各组重复 4 次，报告中位数：

| 场景 | 基线 | 优化版 | 观察到的耗时变化 | 结果比对 |
| --- | ---: | ---: | ---: | ---: |
| 20 次重复读取，缓存 | 660.86 ms | 57.28 ms | 快 91.3% | 80/80 一致 |
| 4 个独立步骤，程序化并行 | 254.33 ms | 66.85 ms | 快 73.7% | 16/16 一致且顺序一致 |
| 显式文件预取，与模拟规划重叠 | 92.95 ms | 76.99 ms | 快 17.2% | 4/4 一致 |

一份 14,013 字符的模拟长结果，在模型视图中缩至 1,645 字符（少 88.3%），完整内容仍可按 ID 加载。这些百分比是**注入等待的工具层微基准**，不应解释成真实对话必然获得同等加速。
原始数值保存在 `tool-optimization-benchmark-results.json`。预取受本地线程调度影响较大，收益尤其不稳定。

### 真实模型配对测试

使用项目配置的 `deepseek-chat`、同一临时工作区和相同问题，交替安排基线/优化版的先后顺序。任务包括单文件读取、JSON 数值读取、目录计数、双文件读取、创建文件、复制文件、可恢复删除。创建/复制/删除通过检查真实文件状态判定，读取任务核对答案内容。优化版启动与生产入口一致的显式文件预取。该测试直接构建 Agent，**未计入 MCP 服务器启动耗时**；MCP 工具定义另作本地测量。

| 指标 | 基线 | 最终优化版 | 变化 |
| --- | ---: | ---: | ---: |
| 任务正确数 | 14/14 | 14/14 | **0 个百分点** |
| 平均整轮耗时 | 1,474.8 ms | 1,159.7 ms | **快 21.37%** |
| 整轮总耗时 | 20,647.5 ms | 16,235.1 ms | 少 4,412.4 ms |
| 平均工具定义 | 1,588 tokens | 346.9 tokens | 少 78.2% |
| 模型可见工具调用 | 17 | 14 | 少 17.6% |

最终计时口径的原始结果见 `tool-optimization-live-results-trial1.json` 和 `tool-optimization-live-results.json`。样本量和模型随机性不足以证明总体任务延迟一定改善；对于几乎没有工具工作的短任务，工具路由和运行时开销也可能抵消收益。

## 验证与剩余限制

`python -m unittest discover -s tests -q`：**40 项通过**。新增检查覆盖动态目录与显式加载、压缩后参数模式不变、缓存命中与文件变更失效、不同调用 ID 的完整结果、显式预取、程序化计划顺序与拒绝写操作、MCP 串行、模型视图压缩而会话原文保持完整。实际 LangChain Agent 循环和 Web、Memory、上下文、MCP 原有用例也通过。

另用假模型经过真实本地 MCP 适配器调用 `time_get_current_time`：返回 1 条非空工具结果，模型每次只收到 5 个相关工具定义（约 679 tokens）。这验证了优化层与实际 MCP 工具执行链能衔接；它不衡量真实模型选择 MCP 工具的准确率。

仍需注意：工具路由是规则式选择，未使用额外意图模型；预测仅识别显式文件路径；缓存不跨进程；大结果只提供预览，模型需要主动加载细节；MCP 进程尚未按需启动。真实模型评估覆盖的是 7 类本地文件任务，尚未量化网页、长期 Memory、多服务器 MCP 或复杂垂直任务的准确率变化。当前结果支持“这批任务正确率保持 100%”，不支持宣称通用准确率提升。
